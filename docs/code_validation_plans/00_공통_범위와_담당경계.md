# 단계 0 - 공통 범위와 담당경계

## 목적

코드검증 구현 전에 모든 단계가 따라야 할 실행 순서, 상태값, 담당 경계, 금지사항을 고정한다. 이 문서는 이후 1~8단계 계획서의 공통 기준이며, 구현자가 단계별 문서를 따를 때 다른 담당자 영역을 침범하지 않도록 막는 기준선이다.

## 구현 반영 상태 (2026-05-22)

- 상태: 코드검증 선행 범위와 주요 통합 범위 완료. schema, classifier, Python 역할 분류, AST/API/context, 등급 판정, config routing, orchestrator validation flow, 제한 런타임, 전처리 metadata semantic gate, whitelist/pending/review, proxy endpoint, 통합 검증 endpoint, B-2 sandbox phase0가 반영됐다.
- 검증 결과: `python -m pytest -q` -> `647 passed, 1 skipped`.
- 경계: 코드검증은 파일별 판정과 evidence 생성을 담당한다. whitelist DB/pending/review/audit/dashboard는 `whitelist` 모듈, 가중치 경로는 `analyzer.service`, B-2 sandbox 증거 수집은 `sandbox/b2`, HTTP 진입점은 `proxy`가 담당한다.
- 제한 런타임은 구현되어 B-1 gate에 연결된다. B-2 sandbox는 증거 수집과 리뷰 보조용이며, clean 결과만으로 release/deployable을 자동 승격하지 않는다.

## 담당 범위

코드검증이 직접 구현하는 범위는 `PYTHON` artifact에 대한 정적 분석과 코드검증 결과 생성이다.

- Python 파일 역할 분류: `CONFIGURATION`, `MODELING`, `PREPROCESSING`, `AUXILIARY`, `UNKNOWN`
- 검증 1: AST 후보 추출. 원본 Python 파일 import 없이 `ast.parse()` 기반 구조와 위험 후보 추출
- 검증 2: `API_POLICY_SCAN` + contextual `safe/review/block`. API alias resolution, blocked/allowed/unregistered/contextual 분류, 문맥 의존 API 판정 연결
- 검증 3: `GRADE_DECISION`. A/B-1/B-2/C 후보와 `PASS/BLOCK/PENDING_REVIEW/ERROR/SKIPPED` 상태 매핑
- `ArtifactValidationResult.details`에 `ast_scan`, `api_scan`, `context_api_scan`, `grade_result`, `runtime_check`, `pending_api_refs`를 남길 수 있는 최소 구조
- `WhitelistLookup` protocol과 `whitelist.integration` adapter 연결
- whitelist/review 모듈과 함께 테스트 가능한 DB/adapter 연결 지점

## 비범위

다음 항목은 현재도 코드검증 단독 책임으로 완성하지 않는다.

- whitelist DB 운영 정책, review 권한/상태 전환 정책, 장기 보존 정책
- 실제 Hugging Face Hub fetch/download 운영화
- proxy 인증/인가, 외부 공개용 rate limit/timeout/retry 정책
- gVisor/runsc 또는 Docker 환경별 운영 배포와 모니터링
- ML-BOM, 서명, append-only audit log
- tokenizer/processor/feature extractor 의미 검증의 최종 자동 승인 정책
- helper/utils/convert/packaging 코드 자동 승인 정책 완성

- 선택 입력: `RuntimeContext`, `WhitelistLookup`, 제한 런타임 loader, source resolver

## 출력

공통 출력은 `ArtifactValidationResult`다.

- `status`: `PASS`, `BLOCK`, `PENDING_REVIEW`, `ERROR`, `SKIPPED`
- `grade`: `A`, `B-1`, `B-2`, `C`, `N/A`
- `review_action`: `AUTO_APPROVE_REGENERATED`, `AUTO_APPROVE`, `SECURITY_OWNER_GATE`, `MANUAL_REVIEW_REQUIRED`, `BLOCK_IMMEDIATELY`, `NONE`
- `reason_entries`: 인터페이스 문서의 공통 reason code 우선 사용
- `details`: 코드검증 세부 결과 확장 dict

## 구현 규칙

- 원본 Python 모델 파일은 검증 단계에서 import하지 않는다.
- 검증 1단계는 파일 내용을 text/bytes로 읽고 `ast.parse()`만 사용한다.
- 검증 1에서는 문맥 의존 API를 후보로만 추출한다.
- 문맥 의존 API의 실제 `safe/review/block` 판정은 검증 2 API 정책 검사 내부에서 한다.
- 문맥 의존 API 분석은 B-2로 간 뒤 하는 검사가 아니라, B-1 후보 유지 / B-2 전환 / BLOCK을 가르는 검증 2 하위 분석이다.
- `open`, `os.path`, `Path`는 이름만으로 `DANGEROUS_CALL`에 넣지 않고 문맥 분석 대상으로만 분류한다.
- 제한 런타임은 B-1 후보를 최종 `PASS`시키기 위한 gate다.
- 제한 런타임은 `code_restricted_runtime` loader를 통해 실행할 수 있다. 위험 코드에는 호출하지 않고 정적 `BLOCK`을 우선한다.
- gVisor/Docker 샌드박스는 B-2/C 후보의 증거 수집과 리뷰 보조용이지 자동 승인 증명이 아니다.
- 명확한 위험 API가 있으면 샌드박스도 실행하지 않고 즉시 `BLOCK`한다.
- `PREPROCESSING`, `AUXILIARY`, `UNKNOWN`은 1차 구현에서 자동 승인하지 않는다.
- `requests`, `urllib`, `httpx`, `socket` 같은 네트워크 API는 모델 코드 내부에서 기본 `BLOCK`이다.
- `torch.nn.*`, `torch.nn.functional.*`, `torch.Tensor.*` 같은 넓은 prefix allowlist를 초기 구현에 넣지 않는다.
- `configuration_*.py` 검증을 위해 원본 파일을 import하거나 `to_dict()`를 호출하지 않는다.
- 데모 코드의 `REVIEW_REQUIRED`를 파일 상태값으로 쓰지 않는다. 파일 상태는 `PENDING_REVIEW`를 사용하고, job 단위 결정에서만 `REVIEW_REQUIRED`를 사용할 수 있다.
- `analyzer/schemas.py`, `analyzer/classifier.py`는 현재 공통 계약으로 사용하므로 변경 시 전체 endpoint와 테스트 호환성을 확인한다.
- proxy는 검증 정책을 소유하지 않고 analyzer/whitelist 통합 함수를 호출한다.
- 코드검증은 운영용 pending store를 직접 호출하지 않고 `pending_api_refs`와 review finding을 남긴다. 영속 저장은 whitelist/review 경로가 담당한다.

필수 공통 케이스:

- 위험 API는 whitelist 여부와 무관하게 `BLOCK`
- 미등록 API는 `B-2/PENDING_REVIEW`

- 문맥 의존 API `block`은 `BLOCK`
- `PREPROCESSING`, `AUXILIARY`, `UNKNOWN`은 위험이 없어도 자동 `PASS`가 아님
- B-1 모델은 runtime gate 통과 없이는 최종 `PASS`가 아님

## 완료 기준

- 최신 단계별 계획서가 기존 최종 설계서와 인터페이스 정의서의 상태값, route kind, reason code를 유지한다.
- 코드검증, whitelist/review, proxy, sandbox 담당 범위가 문서상 분리되어 있다.
- 각 단계 문서가 현재 구현 상태와 남은 안정화 범위를 구분한다.
