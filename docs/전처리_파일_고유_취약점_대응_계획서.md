# 전처리 파일 고유 취약점 대응 계획서

## 1. 현재 구현 상태 요약

이 문서는 `feature/preprocessing-unique-vuln-response` 브랜치의 현재 구현 상태와 전처리 파일 고유 취약점 대응 계획을 동기화한다.

현재 구현은 `analyzer/validators/code_semantic.py` 중심의 semantic inventory, deterministic invariant check, review exposure, sandbox fuzz evidence schema 초안까지 반영되어 있다. 실제 gVisor 실행 runner와 실제 tokenizer/processor import는 아직 구현하지 않았고, 기본 validator 경로에도 연결하지 않았다.

핵심 원칙:

- 전처리 metadata 검증은 Python import나 실행 없이 JSON/text parsing 결과만 사용한다.
- baseline이 없으면 semantic check는 자동 `PASS`가 될 수 없고 `B-2/PENDING_REVIEW` 이상으로 유지한다.
- baseline이 일치하더라도 semantic finding이 있으면 `PASS/APPROVE` 후보가 아니라 review 대상으로 남긴다.
- hidden system injection은 `C/PENDING_REVIEW/MANUAL_REVIEW_REQUIRED`를 유지한다.
- linked Python code가 `BLOCK`이면 semantic review보다 `BLOCK` 우선순위를 유지한다.
- sandbox fuzz 결과는 evidence-only이며 자동 승인 증명이 아니다.
- 실제 untrusted tokenizer/processor import와 gVisor execution runner는 future work다.

## 2. Phase별 완료/남은 항목

| Phase | 상태 | 구현 내용 | 남은 항목 |
| --- | --- | --- | --- |
| Phase 1: metadata inventory | 완료 | tokenizer 및 processor/image/audio metadata inventory 구조화, `tokenizer_config.json` config routing 통합 | 운영 baseline store 연동 |
| Phase 2: deterministic invariant check | 완료 | tokenizer, processor, image, audio invariant finding 생성 및 fail-closed 판정 | 정책 threshold 운영 튜닝 |
| Phase 3: sandbox semantic fuzz | 부분 완료 | evidence schema와 opt-in runner interface 구현 완료 | 실제 gVisor execution runner, 실제 tokenizer/processor import, corpus 실행 미구현 |
| Phase 4: review exposure | 부분 완료 | validation result details, config reason entries, job summary evidence 노출 일부 완료 | persistent review queue, 승인 workflow, UI/report 연동 미구현 |

## 3. Phase 1: semantic metadata inventory

상태: 완료

구현 파일:

- `analyzer/validators/code_semantic.py`
- `analyzer/validators/config_validator.py`
- `analyzer/orchestrator.py`
- `tests/test_code_semantic.py`
- `tests/test_config_validator.py`
- `tests/test_validation_flow.py`

완료된 항목:

- `tokenizer.json`, `tokenizer_config.json`, `special_tokens_map.json`, `added_tokens.json`, `vocab.json`, `merges.txt`, `chat_template.jinja`에서 리뷰 가능한 `details["semantic_inventory"]`를 생성한다.
- `preprocessor_config.json`, `processor_config.json`에서 image/audio/processor 관련 inventory를 구조화한다.
- special token map, added token, vocab size, merge rule count, `model_max_length`, `padding_side`, `truncation_side`, `split_special_tokens`, `clean_up_tokenization_spaces`를 inventory에 남긴다.
- image config의 `do_resize`, `size`, `crop_size`, `do_rescale`, `rescale_factor`, `do_normalize`, `image_mean`, `image_std`, channel/data format hint를 기록한다.
- audio config의 `sampling_rate`, `padding_value`, `do_normalize`, `feature_size`, `return_attention_mask`, `max_length`, `truncation`, `padding` 관련 값을 기록한다.
- processor config의 `processor_class`, `tokenizer_class`, `image_processor_class`, `feature_extractor_class`, `chat_template`, 하위 component ref를 기록한다.
- `chat_template`은 단순 hash만 남기지 않고 system/user/assistant/tool/document/add_generation_prompt hint와 finding을 남긴다.
- `tokenizer_config.json`은 `config_validator` 경유 시에도 기존 custom class, `trust_remote_code`, linked Python routing을 유지하면서 `semantic_check`, `semantic_inventory`, `semantic_findings`를 최종 details에 포함한다.

완료 기준:

- baseline이 없으면 `BASELINE_MISSING`과 함께 `B-2/PENDING_REVIEW/SECURITY_OWNER_GATE`로 유지한다.
- baseline 일치와 finding 없음이 동시에 만족될 때만 `PASS` 후보가 된다.
- metadata inventory 생성은 Python import/실행 없이 JSON/text parsing만 사용한다.

## 4. Phase 2: deterministic invariant check

상태: 완료

완료된 tokenizer invariant:

- special token 문자열 중복/충돌 탐지
- `additional_special_tokens`와 bos/eos/unk/pad/cls/sep/mask 충돌 탐지
- added token id/content 중복 탐지
- `split_special_tokens=True` 탐지
- AddedToken `lstrip`, `rstrip`, `normalized=False` 위험 옵션 탐지
- `model_max_length` 과도값 또는 비정상값 탐지
- `padding_side`, `truncation_side`가 `left/right` 외 값이면 review finding 생성
- chat template hidden system injection은 `C/PENDING_REVIEW/MANUAL_REVIEW_REQUIRED` 유지

완료된 processor/image/audio invariant:

- `processor_config.json`의 tokenizer/image_processor/feature_extractor component ref 누락 또는 비정상 타입 탐지
- `processor_class`, `tokenizer_class`, `image_processor_class`, `feature_extractor_class` 비정상 타입 탐지
- processor `chat_template`의 media placeholder와 image/video/audio 관련 literal finding 생성
- URL/path-like literal은 `NETWORK_OR_PATH_REVIEW` finding으로 유지
- image `size`, `crop_size`, `image_mean`, `image_std`, `rescale_factor`, bool field, channel/data format 검증
- audio `sampling_rate`, `padding_value`, `feature_size`, `max_length`, `truncation`, `padding`, `return_attention_mask` 검증

판정 기준:

- invariant finding은 기본적으로 `B-2/PENDING_REVIEW/SECURITY_OWNER_GATE`로 남긴다.
- hidden system injection은 `C/PENDING_REVIEW/MANUAL_REVIEW_REQUIRED`로 남긴다.
- linked Python `BLOCK`이 있으면 config/tokenizer_config 최종 status는 기존처럼 `BLOCK` 우선이다.
- baseline 일치 + finding 없음인 경우만 `PASS` 후보가 된다.

## 5. Phase 3: sandbox semantic fuzz

상태: 부분 완료

완료된 항목:

- tokenizer/processor sandbox fuzz evidence schema를 `code_semantic.py`에 정의했다.
- `SemanticFuzzRunnerConfig`에 다음 runner config 필드를 포함했다.
  - `revision_pin`
  - `offline_mode`
  - `network_disabled`
  - `read_only_snapshot`
  - `sandbox_runtime`
  - `cpu_budget_cores`
  - `memory_budget_mb`
  - `time_budget_ms`
  - `require_phase0_import_closure_passed`
- `SemanticFuzzPrerequisites`로 Phase 0 정적 검증과 Python import closure PASS 전제를 명시했다.
- `SemanticFuzzCaseEvidence`와 `SemanticFuzzOutputSnapshot`에 다음 evidence 필드를 포함했다.
  - `input_hash`
  - output `key/shape/dtype`
  - `token_count`
  - `special_token_mask`
  - `offset_mapping`
  - `media_placeholder_count`
  - `runtime_events`
- `SemanticFuzzBaselineDiff`로 baseline tokenizer/processor가 있을 때 diff를 저장할 구조를 정의했다.
- `PreprocessingSemanticFuzzRunner` Protocol로 future opt-in runner 인터페이스를 정의했다.
- `validate_preprocessing_metadata_artifact(..., sandbox_fuzz_result=...)`는 opt-in evidence를 받을 수 있지만, 이 evidence는 `SANDBOX_FUZZ_EVIDENCE_REVIEW` finding으로만 노출된다.

미구현/future work:

- 실제 gVisor/runsc execution runner
- 실제 tokenizer/processor import와 실행
- Hugging Face artifact snapshot mount와 read-only filesystem 적용
- corpus 기반 tokenizer/processor fuzz 입력 생성
- baseline tokenizer/processor 로딩과 실제 output diff 계산
- runtime event 수집의 운영 구현
- orchestrator 기본 validation path 자동 연결

완료 기준:

- sandbox fuzz evidence schema는 JSON 직렬화 가능해야 한다.
- baseline이 없으면 invariant-only 또는 fuzz-only evidence가 있어도 자동 승인하면 안 된다.
- sandbox fuzz는 별도 opt-in runner로만 실행 가능해야 하며 기본 validator path에서 untrusted processor/tokenizer를 import하지 않는다.
- Phase 0 정적 검증을 통과한 Python import closure만 sandbox fuzz 대상이 된다는 전제를 runner config/prerequisite에 남긴다.

## 6. Phase 4: semantic finding review exposure

상태: 부분 완료

완료된 항목:

- `ArtifactValidationResult.details`에 `semantic_findings`와 `semantic_finding_codes`가 유지된다.
- `tokenizer_config.json`이 `config_validator` 경유 시에도 `semantic_check`, `semantic_inventory`, `semantic_findings`, `semantic_finding_codes`가 최종 details에 포함된다.
- config validator reason entry에 semantic finding code가 노출된다.
- job-level summary reason entry에 `repo_path:FINDING_CODE` 형태의 semantic evidence가 노출된다.
- `semantic_check.status`가 `REVIEW`, `FAILED`, `ERROR`, `BASELINE_MISSING`이면 stale PASS 결과가 있어도 job-level `APPROVE`로 내려가지 않도록 guard를 추가했다.
- hidden system injection은 `C/PENDING_REVIEW/MANUAL_REVIEW_REQUIRED` 흐름으로 유지된다.
- linked Python `BLOCK` 우선순위는 유지된다.

미구현/future work:

- persistent review queue 연동
- reviewer assignment와 SLA 관리
- security owner 승인/반려 workflow
- review decision을 whitelist/baseline store에 반영하는 운영 flow
- UI/report에서 semantic finding별 상세 evidence 렌더링

완료 기준:

- semantic finding이 validation result와 job summary에서 숨겨진 채 `PASS/APPROVE`로 내려가면 안 된다.
- review queue가 아직 없어도 후속 reviewer가 `semantic_findings`, `semantic_finding_codes`, summary evidence만 보고 검토 대상을 식별할 수 있어야 한다.
- persistent review queue 미연동 상태에서는 `review_queue_entry_id = null`로 유지한다.

## 7. 자동 승인 금지 규칙

다음 조건에서는 자동 승인 금지:

- baseline이 없는 metadata artifact
- semantic invariant finding이 있는 artifact
- hidden system injection finding이 있는 artifact
- sandbox fuzz evidence만 있고 baseline diff가 없거나 review finding이 남은 artifact
- `semantic_check.status`가 `REVIEW`, `FAILED`, `ERROR`, `BASELINE_MISSING`인 artifact
- linked Python code가 `PENDING_REVIEW`, `ERROR`, `MISSING`, `BLOCK`인 config/tokenizer_config artifact

`PASS` 후보 조건:

- baseline이 존재한다.
- 현재 artifact content hash가 baseline과 일치한다.
- review severity semantic finding이 없다.
- linked Python code가 있으면 모두 `PASS`다.
- sandbox fuzz evidence가 있더라도 review finding을 만들지 않는 별도 정책이 확정되어야 한다. 현재 구현에서는 fuzz evidence가 있으면 review evidence로 남긴다.
