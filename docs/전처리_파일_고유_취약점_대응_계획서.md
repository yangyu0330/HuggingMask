# 전처리 파일 고유 취약점 대응 계획서

## 1. 목적

`tokenization_*.py`, `processing_*.py`, `image_processing_*.py`, `feature_extraction_*.py`는 일반 Python 코드 실행 위험과 별도로 모델 입력 의미를 바꾸는 위험이 있다. 이 문서는 tokenizer/processor 계열 파일을 자동 승인하지 않는 현재 정책을 유지하면서, 후속 semantic/invariant 검증을 구현하기 위한 조사 결과와 단계별 대응 계획을 정의한다.

## 2. 조사 근거

- Hugging Face Transformers의 custom code 로딩은 `trust_remote_code=True`일 때 Hub의 코드를 로컬에서 실행할 수 있으므로, 신뢰 저장소와 코드 검토가 전제되어야 한다. 전처리 파일도 custom processor/tokenizer 경로에 포함될 수 있으므로 단순 파일명 기반 허용은 금지한다. 참고: [Transformers Auto Classes](https://huggingface.co/docs/transformers/main/en/model_doc/auto), [Loading custom models](https://huggingface.co/docs/transformers/main/models).
- chat template은 tokenizer/processor가 대화 메시지를 모델 입력 문자열로 바꾸는 규칙이다. 잘못된 control token이나 role 경계는 모델 성능과 지시 해석을 크게 바꿀 수 있고, multimodal 모델에서는 `chat_template`이 tokenizer가 아니라 processor에 저장될 수 있다. 참고: [Chat templates](https://huggingface.co/docs/transformers/chat_templating), [Writing a chat template](https://huggingface.co/docs/transformers/en/chat_templating_writing), [Processors](https://huggingface.co/docs/transformers/en/main_classes/processors).
- tokenizer의 special token, padding, truncation, `split_special_tokens`, `clean_up_tokenization_spaces` 같은 옵션은 입력 토큰 경계, attention mask, 로그/디코딩 결과에 영향을 준다. 참고: [Tokenizer](https://huggingface.co/docs/transformers/v4.34.0/main_classes/tokenizer), [Padding and truncation](https://huggingface.co/docs/transformers/v4.52.3/en/pad_truncation).
- image processor는 이미지 크기, crop, resize, rescale, normalize 값을 모델 입력 tensor로 변환한다. 이 값이 바뀌면 코드 실행 위험이 없어도 모델 판단 의미가 바뀐다. 참고: [Image processors](https://huggingface.co/docs/transformers/main/image_processors).
- feature extractor는 audio raw signal을 모델 입력 tensor로 바꾸며 sampling rate, padding, truncation, resampling이 모델 입력 의미를 결정한다. 참고: [Feature extractors](https://huggingface.co/docs/transformers/feature_extractors).
- Hugging Face Hub는 repository 파일을 malware scan하지만, 스캔 완료 전/오류 상태가 있을 수 있고 malware scan은 semantic 변조를 증명하지 않는다. 참고: [Hub malware scanning](https://huggingface.co/docs/hub/en/security-malware).

## 3. 위협 모델

### 3.1 공통 실행 위험

- top-level import side effect: 파일 import 또는 class registration 과정에서 파일/네트워크/환경 접근이 발생한다.
- `trust_remote_code`, `auto_map`, `processor_class`, `tokenizer_class`가 custom Python class를 로드한다.
- alias/from-import 우회로 `torch.load`, `pickle.load`, `numpy.load(allow_pickle=True)`, `requests.get`, `subprocess.run` 같은 위험 호출이 숨겨진다.
- `__getattr__`, dynamic import, registry pattern, Jinja/render helper가 실제 호출 대상을 늦게 결정한다.

### 3.2 tokenizer 고유 위험

- special token ID, `bos/eos/unk/pad/cls/sep/mask` 매핑 변경으로 모델 입력 경계가 바뀐다.
- `additional_special_tokens`나 multimodal placeholder token이 의도와 다르게 추가, 삭제, 재사용된다.
- `chat_template`이 system/user/assistant role 경계를 바꾸거나 숨은 system 지시를 삽입한다.
- `split_special_tokens=True`, `AddedToken(lstrip/rstrip/normalized=False)` 같은 옵션으로 control token 경계가 흐려진다.
- Unicode normalize, zero-width 문자, homoglyph, 전각/반각 처리로 사람이 보는 문자열과 tokenized input이 달라진다.
- token 수 팽창 또는 `truncation_side`, `model_max_length`, `padding_side` 조작으로 중요한 앞/뒤 문맥이 잘린다.
- `decode(skip_special_tokens=True)` 의존 로그에서 control token이 사라져 감사 추적이 왜곡된다.

### 3.3 processor 계열 고유 위험

- `processing_*.py`가 tokenizer, image processor, feature extractor를 묶으며 하위 구성요소를 바꿔치기한다.
- multimodal `apply_chat_template`에서 image/video/audio placeholder 수와 실제 media item 수가 불일치한다.
- `pixel_values`, `input_values`, `image_grid_thw`, `video_grid_thw`, `attention_mask` key 또는 shape가 모델 기대와 다르게 만들어진다.
- URL/path 입력을 직접 열어 외부 fetch, 로컬 파일 접근, 대용량 media 로드가 발생한다.
- tools/documents/RAG 입력을 chat template에 섞으면서 사용자/시스템/도구 role 경계가 오염된다.

### 3.4 image processor 고유 위험

- resize/crop/interpolation, RGB/BGR 변환, EXIF orientation 처리 차이로 시각 의미가 바뀐다.
- `image_mean`, `image_std`, `rescale_factor`, `do_normalize`, `do_rescale` 변경으로 입력 분포가 모델 학습 분포와 달라진다.
- 초고해상도 이미지, 많은 이미지 batch, 반복 resize로 CPU/GPU/메모리 DoS가 발생한다.
- PIL/torchvision backend 차이 또는 dtype/channel layout 차이가 재현성을 깨뜨린다.

### 3.5 feature extractor 고유 위험

- audio `sampling_rate` 불일치, resampling 방식 변경, silence padding 값 변경으로 음성 의미가 달라진다.
- truncation/padding 정책으로 앞/뒤 발화가 잘리거나 silence가 과도하게 추가된다.
- feature scaling, normalization, channel mixing, mono/stereo 변환이 모델 입력 분포를 바꾼다.
- 긴 audio/video 입력으로 처리 시간과 메모리 사용량이 과도하게 늘어난다.

## 4. 판정 원칙

- 전처리 계열 파일은 semantic/invariant 검증이 통과하기 전까지 `B-1/PASS`가 될 수 없다.
- 명확한 실행 위험은 sandbox로 보내지 않고 `C/BLOCK` 또는 `C/PENDING_REVIEW`로 남긴다.
- 실행 위험은 없지만 의미 변조 가능성이 있으면 `B-2/PENDING_REVIEW/SECURITY_OWNER_GATE`로 둔다.
- malware scan, restricted runtime, gVisor 실행 성공은 전처리 의미 보존의 증명이 아니다.
- 최종 승인 판단은 source diff, metadata diff, deterministic semantic check, sandbox evidence, 사람 리뷰가 모두 연결되어야 한다.

## 5. 대응 계획

### Phase 0 - 현재 방어선 고정

목표:

- tokenizer/processor 계열 자동 승인 금지를 정책과 테스트에 고정한다.
- PR #23류 구현에서 공개 진입점과 alias/from-import 탐지를 먼저 완성한다.

구현:

- `analyzer/validators/code_roles.py`의 `PREPROCESSING` + `preprocess_kind` 분류를 결과 detail에 항상 보존한다.
- `analyzer/validators/code_ast.py` 또는 preprocessing validator에서 alias map과 from-import resolution을 공통 함수로 사용한다.
- `validate_python_artifact()`와 전처리 전용 진입점이 동일한 `ArtifactValidationResult` 계약을 반환하게 한다.
- `tests/` 아래 실행 불가 데모는 제거하거나 `scripts/`로 이동하고, pytest 회귀 테스트만 남긴다.

테스트:

- `import torch as t; t.load(...)` -> `C/BLOCK`
- `from torch import load; load(...)` -> `C/BLOCK`
- `import numpy as np; np.load(..., allow_pickle=True)` -> `C/BLOCK`
- 정상 `tokenization_*.py`, `processing_*.py`, `image_processing_*.py`, `feature_extraction_*.py` -> `B-2/PENDING_REVIEW`

### Phase 1 - metadata-only semantic inventory

목표:

- Python 실행 없이 bundle metadata를 수집해 리뷰 가능한 diff를 만든다.

대상 파일:

- tokenizer: `tokenizer.json`, `tokenizer_config.json`, `special_tokens_map.json`, `vocab.json`, `merges.txt`, `chat_template.jinja`
- processor/image/audio: `preprocessor_config.json`, `processor_config.json`, `config.json`

구현:

- `analyzer/validators/code_semantic.py` 추가
- `TokenizerSemanticInventory`, `ProcessorSemanticInventory` dataclass 추가
- `tokenizer.json`, `special_tokens_map.json`, `added_tokens.json`, `vocab.json`, `merges.txt`, `preprocessor_config.json`, `processor_config.json`, `chat_template.jinja`는 `OTHER`로 흘려보내지 않고 전처리 semantic scan 대상으로 분류한다.
- 전처리 metadata route는 `PREPROCESSING_SEMANTIC_SCAN`으로 분리하고, baseline 없는 결과는 fail-closed로 `B-2/PENDING_REVIEW`에 머물게 한다.
- JSON/YAML은 structured parser로 읽고, Python source는 AST만 사용한다.
- `details["semantic_inventory"]`에 hash, key field, suspicious delta를 기록한다.
- `details["semantic_check"]`에는 `PASSED`, `REVIEW`, `FAILED`, `SKIPPED`, `ERROR`, `BASELINE_MISSING` 상태를 남긴다.

탐지 항목:

- special token map 변경, unknown token 재정의, placeholder token 충돌
- chat template 존재, hash, role token literal, tool/document branch 존재
- padding/truncation/max length/side 변경
- image size, crop, normalize/rescale, channel order, backend hint
- audio sampling rate, feature size, padding value, return key

### Phase 2 - deterministic invariant check

목표:

- 외부 네트워크와 임의 Python import 없이 정적/메타데이터 기반 invariant를 판정한다.

검사:

- tokenizer:
  - special token 문자열과 ID가 서로 충돌하지 않는지 확인
  - chat template에 system/user/assistant role token이 비정상적으로 재배치되지 않았는지 확인
  - `split_special_tokens=True`, 위험한 `AddedToken` 옵션, 과도한 `model_max_length` 변경 탐지
  - audit log용 decode 정책에 control token visibility를 강제
- processor:
  - multimodal placeholder token 수와 media item 수를 검증할 수 있는 hook 설계
  - 하위 tokenizer/image processor/feature extractor 참조를 재귀 검증 대상으로 등록
  - URL/path 후보를 `NETWORK_OR_PATH_REVIEW`로 기록
- image processor:
  - `do_resize`, `size`, `crop_size`, `do_normalize`, `image_mean/std`, `rescale_factor`를 모델 config와 비교
  - max pixels, max images, dtype/channel layout 제한
- feature extractor:
  - `sampling_rate`, `padding_value`, `do_normalize`, max audio seconds 제한
  - resampling/truncation/padding 정책 변경을 `REVIEW` 이상으로 기록

판정:

- invariant 실패 또는 기준 부재 -> `B-2/PENDING_REVIEW`
- baseline이 없는 semantic check는 비교 증거가 없는 상태이므로 `PASS`가 아니라 `BASELINE_MISSING` + `B-2/PENDING_REVIEW`로 고정한다.
- `numpy.load`는 Phase 2에서 `allow_pickle=False`, 상수 resource path, 확장자/크기 제한을 모두 검증하기 전까지 fail-closed로 `C/BLOCK`을 유지한다.
- hidden role injection, path/network access, 과도한 resource budget 초과 -> `C/PENDING_REVIEW` 또는 `BLOCK`

### Phase 3 - sandbox semantic fuzz

목표:

- gVisor/Docker 환경에서만 전처리 객체를 제한적으로 로드하고 golden corpus 출력 차이를 수집한다.

전제:

- revision pin, offline mode, network disabled
- read-only snapshot, temp output directory 제한
- CPU/memory/time/file count budget
- tokenizer/processor import closure의 모든 Python 파일이 Phase 0 정적 검증을 통과해야 함

golden corpus:

- tokenizer: ASCII, Unicode normalize, zero-width, homoglyph, control token, long prompt, chat role corpus
- processor: text-only, image+text, multi-image, missing media, tools/documents branch corpus
- image: RGB/BGR, EXIF orientation, extreme aspect ratio, max resolution boundary
- audio: sampling rate mismatch, silence, long audio, stereo/mono boundary

evidence:

- input hash, output key/shape/dtype, token count, special token mask, offset mapping, media placeholder count, runtime events
- baseline tokenizer/processor가 있으면 baseline diff 저장
- baseline이 없으면 invariant-only 결과로 두고 자동 승인 금지

### Phase 4 - review workflow 통합

목표:

- semantic 결과를 사람이 재현 가능한 리뷰 항목으로 만든다.

구현:

- `details["tokenizer_semantic_check"]`, `details["processor_semantic_check"]`를 공통 schema로 정의
- `semantic_findings[]`에 `code`, `severity`, `evidence`, `recommended_action` 기록
- `review_findings`와 pending queue에 semantic finding을 노출
- 승인 시 whitelist/API 승인과 별도로 semantic approval record를 남긴다.

완료 기준:

- 전처리 파일은 semantic check가 `PASSED`이고 실행/API/metadata risk가 없을 때만 B-1 후보가 될 수 있다.
- semantic check가 `SKIPPED`, `ERROR`, `REVIEW`이면 무조건 `B-2/PENDING_REVIEW` 이상이다.
- semantic finding을 숨긴 채 `PASS`로 내려가는 경로가 테스트로 막혀 있다.

## 7. 1차 보강 반영 기준

이번 보강에서는 자동 승인 방지를 먼저 코드와 테스트에 고정한다.

- `FileKind`에 `TOKENIZER_JSON`, `SPECIAL_TOKENS_MAP_JSON`, `ADDED_TOKENS_JSON`, `VOCAB_JSON`, `MERGES_TXT`, `PREPROCESSOR_CONFIG_JSON`, `PROCESSOR_CONFIG_JSON`, `CHAT_TEMPLATE_JINJA`를 추가한다.
- `analyzer/classifier.py`는 위 파일들을 `OTHER`가 아니라 전처리 metadata 종류로 분류한다.
- `analyzer/orchestrator.py`는 전처리 metadata를 `PREPROCESSING_SEMANTIC_SCAN`으로 라우팅한다.
- `analyzer/validators/code_semantic.py`는 metadata hash, key field, chat template hint, `semantic_findings[]`를 기록한다.
- baseline이 없으면 `details["semantic_check"]["status"] == "BASELINE_MISSING"`이며 결과는 `B-2/PENDING_REVIEW/SECURITY_OWNER_GATE`이다.
- hidden system injection hint가 있는 chat template은 `CHAT_TEMPLATE_HIDDEN_SYSTEM_INJECTION` finding과 함께 `C/PENDING_REVIEW/MANUAL_REVIEW_REQUIRED`로 남긴다.
- `import torch as t; t.load(...)`, `from torch import load; load(...)`, `np.load(..., allow_pickle=True)`, `np.load(..., allow_pickle=False)`는 현재 정책에서 모두 `C/BLOCK` 회귀 테스트로 고정한다.

## 8. PR #23에 대한 즉시 적용 기준

PR #23 같은 전처리 validator PR은 아래를 만족하기 전까지 merge하지 않는다.

- `analyzer.schemas` 또는 실제 공통 schema import가 성공한다.
- 전처리 진입점이 `ArtifactValidationResult`를 반환한다.
- alias/from-import 위험 호출 회귀 테스트가 통과한다.
- `tests/` 아래 깨진 데모 파일이 제거되거나 pytest가 아닌 위치로 이동한다.
- 전처리 파일 자동 `B-1/PASS` 금지 테스트가 유지된다.
