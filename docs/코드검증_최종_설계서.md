## 1. 문서 목적

이 문서는 HuggingMask의 Python 커스텀 코드 검증 부분을 실제 구현하기 위한 최종 설계 기준이다. 기존 프로젝트 계획서, 최종 아키텍처, 복잡도 등급 분류 설계, 추가 메모 문서, `test_HuggingMask` 데모 검증 코드를 종합해 작성했다.

이 문서의 목적은 다음과 같다.

- 1차 구현 대상인 `configuration_*.py`, `modeling_*.py` 등 Hugging Face 커스텀 Python 파일의 검증 기준을 고정한다.
- 기존 3단계 검증 구조인 AST 분석, API 화이트리스트, 복잡도 등급 분류를 실제 `HuggingMask` 계약에 맞춘다.
- 과차단을 줄이기 위해 파일 역할 기반 라우팅과 문맥 의존 API 분석을 추가한다.
- tokenizer, processor, 보조/변환/패키징형은 1차 구현 범위에서 제외하고, 추후 별도 설계가 필요함을 명확히 한다.
- Codex가 이후 실제 코드를 작성할 때 모듈 경계, 테스트 기준, 우선순위를 혼동하지 않도록 한다.

## 1.1 현재 개발 전제와 양유상 구현 범위

현재 팀원들은 아직 본격 개발에 돌입하지 않은 상태다. 따라서 양유상이 먼저 진행할 코드 검증 구현은 다른 담당자의 완성 모듈에 강하게 의존하면 안 된다.

양유상 선행 구현 범위:

- `PYTHON` artifact에 대한 코드 역할 분류
- AST 기반 정적 분석
- API 호출 추출과 임시 whitelist 판정
- 문맥 의존 API 분석
- 설정형(`CONFIGURATION`)과 모델 실행형(`MODELING`) 코드 검증
- A/B-1/B-2/C 등급 후보 산출
- `ArtifactValidationResult` 형태의 코드 검증 결과 생성

선행 구현에서 직접 완성하지 않는 범위:

- tokenizer, processor, feature extractor 등 입력 전처리/변환형 검증
- helper, utils, convert, packaging, 동적 `__init__.py` 등 보조/변환/패키징형 검증
- 최종 `ValidationJobResponse` 조립 정책 전체
- 정식 adaptive whitelist 저장소와 보안 담당자 승인 workflow
- 실제 gVisor/runsc 샌드박스 운영
- ML-BOM, 서명, append-only audit log
- proxy endpoint 전체 통합

위 범위는 이후 팀원 모듈과 통합할 때 연결한다. 선행 구현 단계에서는 필요한 경우 `WhitelistLookup` 같은 작은 protocol 또는 in-memory policy adapter를 코드 검증 내부에 두고, 정식 `whitelist` 모듈이 생기면 교체한다.

1차 구현에서 `PREPROCESSING`, `AUXILIARY`, `UNKNOWN` 역할 파일은 위험 패턴을 공통 AST/API 레벨에서 탐지할 수는 있지만, 자동 승인 대상이 아니다. 정책이 확정되기 전까지는 `PENDING_REVIEW` 또는 `SKIPPED`로 남기고, 설정형과 모델 실행형만 최종 코드검증 판정 대상으로 삼는다.

## 3. 전체 위치

코드 검증은 HuggingMask 전체 파이프라인에서 `PYTHON`, `CONFIG_JSON`, `TOKENIZER_CONFIG_JSON` artifact를 다룬다.

전체 흐름은 다음과 같다.

```text
ValidationJobRequest
  -> ArtifactRef 목록
  -> file classifier
  -> config/tokenizer config trigger scan
  -> referenced .py routing
  -> code validator
       0. role classification
       1. CODE_AST_SCAN
          - 파일 역할 분류 보조 신호 추출
          - 위험 import/call, 동적/난독화 패턴 추출
          - API 호출 목록과 문맥 의존 API 후보 추출
       2. API_POLICY_SCAN
          - alias resolution
          - blocked/위험 범주/allowed/unregistered 판정
          - 문맥 의존 API 후보를 context analyzer로 safe/review/block 판정
       2.5 tokenizer semantic verification (future scope)
       2.6 processor semantic verification (future scope)
       3. grade decision
       4. runtime action
  -> ArtifactValidationResult
  -> orchestrator
  -> ValidationJobResponse
```

코드 검증 validator는 최종 job 상태를 직접 결정하지 않는다. 파일별 `ArtifactValidationResult`만 반환하고, 전체 `overall_status`와 `overall_decision`은 `analyzer/orchestrator.py`가 계산한다.

### 3.1 코드 검증 내부 실행 순서 고정

코드 검증 내부 순서는 아래처럼 고정한다.

```text
0. config 라우팅
   - auto_map / trust_remote_code / custom_pipelines 확인
   - 참조 .py를 코드 검증으로 연결

1. AST 분석
   - 원본 import 금지
   - ast.parse만 수행
   - 파일 역할 분류
   - 위험 call/import 후보 탐지
   - 동적/난독화 패턴 탐지
   - 호출 API 목록 추출
   - 문맥 의존 API 후보 추출

2. API 검사 + 문맥 의존 API 분석
   - blocked_exact / blocked_prefix 검사
   - 네트워크/프로세스/역직렬화/native loading 검사
   - contextual API면 context analyzer 실행
   - allowed_exact 검사
   - 나머지는 UNREGISTERED

3. 정적 판정
   - A 후보
   - B-1 후보
   - B-2 후보
   - C 후보
   - BLOCK

4. route별 후속 처리
   - A 후보: 원본 실행 없이 코드 재생성
   - B-1 후보: 제한 런타임 실행
   - B-2/C 후보: gVisor/Docker 샌드박스 또는 리뷰 큐
   - BLOCK: 실행하지 않음
```

문맥 의존 API 분석은 B-2로 보낸 뒤 실행하는 검사가 아니다. 검증 2에서 먼저 수행하고, 그 결과가 B-1 후보 유지, B-2 전환, BLOCK을 결정한다.

제한 런타임은 정적으로 안전해 보이는 B-1 후보를 최종 PASS시키기 위한 gate다. gVisor/Docker 샌드박스는 자동 승인 불가한 B-2/C 후보를 격리해 증거를 수집하거나 리뷰를 보조하는 환경이다. 명확한 위험 API가 발견된 파일은 샌드박스도 실행하지 않고 즉시 BLOCK한다.

## 4. 설계 원칙

### 4.1 원본 Python 모듈은 검증 단계에서 import하지 않는다

`.py` 파일은 import 순간 top-level 코드가 실행될 수 있다. 따라서 검증 1단계에서는 반드시 텍스트로 읽고 `ast.parse()`만 수행한다.

금지:

- `importlib.import_module()`로 원본 로드
- `spec.loader.exec_module()`로 원본 실행
- `from_pretrained(..., trust_remote_code=True)`를 검증 전 호출

허용:

- 파일 내용을 bytes/text로 읽기
- `ast.parse()`
- AST 노드 기반 구조 분석
- 제한 런타임 또는 샌드박스 단계에서만 통제된 실행

### 4.2 "위험 가능성"과 "악성 확정"을 분리한다

`eval`, `exec`, `__import__`, `os.system`, `subprocess`, `socket` 등은 자동 승인 경로에서 정당화하기 어렵기 때문에 차단한다.

반면 `open`, `os`, `Path`는 이름만으로 악성 확정은 아니다. 파일군과 인자 문맥에 따라 다르게 처리한다.

`requests` 등 네트워크 API는 별도로 본다. 원격 모델 코드 내부에서 네트워크를 직접 여는 행위는 검증 엔진이 통제할 수 없는 외부 효과를 만들기 때문에 기본 `BLOCK`이다. 모델 metadata 조회처럼 정상적으로 필요한 네트워크 접근은 스캔 대상 코드가 직접 수행하지 않고, 프록시나 검증 엔진의 통제된 downloader가 대신 수행해야 한다.

예:

- `open("vocab.json", "r")`: tokenizer/processor 계열에서 제한 허용 후보
- `open(user_input, "w")`: 위험
- `os.path.join(...)`: path helper 후보
- `os.system(...)`: 즉시 차단
- `requests.get(...)`: 모델 코드 내부에서는 기본 차단

### 4.3 모듈 단위 허용이 아니라 API 호출 단위로 판단한다

`torch`를 import했다고 전체를 허용하지 않는다. 실제 호출된 API를 추출하고, API 단위로 `ALLOWED`, `BLOCKED`, `UNKNOWN/PENDING`을 판정한다.

예:

- 허용 후보: `torch.nn.Linear`, `torch.nn.functional.relu`, `torch.tensor`
- 차단: `torch.load`, `pickle.load`, `numpy.load`
- 미등록: 공식 문서나 기존 whitelist에 없는 신규 API

### 4.4 모르면 안전한 등급으로 넣지 않는다

역할 분류가 애매하면 자동 승인 등급으로 보내지 않는다.

- 설정형인지 애매하면 A 금지
- 모델 실행형인지 애매하면 B-1 금지
- 전처리형과 보조/변환/패키징형은 1차 구현에서 자동 승인 금지
- 보조/변환/패키징형은 기본적으로 일반 배포 승인 경로에서 제외

### 4.5 가장 높은 위험도가 전체 파일 등급을 결정한다

파일 내부 대부분이 안전해도 일부에서 위험 패턴이 발견되면 더 높은 위험 등급을 적용한다.

우선순위:

1. 위험 import / 위험 call / 위험 API -> `BLOCK`
2. 동적/난독화/비정형 패턴 -> `C`
3. 미등록 API -> `B-2`
4. 정형 모델 구조 + 허용 API + 문맥 의존 API safe + 제한 런타임 gate 통과 -> `B-1`
5. 단순 설정 클래스 -> `A`

### 4.6 코드검증과 whitelist/review 모듈의 담당 경계

선행 구현에서는 코드검증이 AST/API/context 분석과 등급 후보 산출을 담당하고, 운영용 whitelist DB와 리뷰 workflow는 다른 모듈의 책임으로 둔다.

| 영역 | 담당 | 설명 |
|---|---|---|
| API 호출 추출 | 코드검증 | AST에서 `torch.nn.Linear`, `F.relu`, `torch.load` 같은 호출 경로 추출 |
| alias resolution | 코드검증 | `import torch.nn.functional as F` -> `torch.nn.functional`로 해석 |
| 위험 API 선차단 | 코드검증 | `eval`, `subprocess`, `requests`, `torch.load` 등 명확한 위험은 whitelist 질의 전에 `BLOCK` 가능 |
| 문맥 의존 API 분석 | 코드검증 | `open`, `os.path`, `Path` 등을 context analyzer로 `safe/review/block` 판정 |
| whitelist 질의 인터페이스 | 코드검증 | `WhitelistLookup` protocol, mock/in-memory adapter 제공 |
| 실제 whitelist DB | whitelist 담당 모듈 | 허용 API 저장소, 정책 버전, 승인 상태 관리 |
| Pending API 저장 | whitelist/review 담당 모듈 | 미등록 API 등록/갱신, seen count, first_seen/last_seen 관리 |
| 보안 담당자 승인 workflow | review 담당 모듈 | 리뷰 결정, whitelist 반영, 감사 로그 연결 |
| 공식 문서/Verified Org 판단 | whitelist/review 담당 모듈 | API가 공식 문서에 있는지, 검증된 조직 사용 여부 판단 |

## 5. 실제 저장소 계약과 맞춘 상태값

`HuggingMask_인터페이스정의서_v1_0_Notion.md` 기준으로 상태값을 사용한다.

### 5.1 RouteKind

- `CODE_AST_SCAN`: AST 구조 분석
- `CODE_RESTRICTED_RUNTIME`: B-1 제한 런타임
- `CODE_SANDBOX_RUNTIME`: B-2/C 샌드박스
- `CONFIG_SCHEMA_VALIDATION`: config/tokenizer config 트리거 검증

### 5.2 ValidationStatus

- `PASS`: 자동 통과
- `BLOCK`: 즉시 차단
- `PENDING_REVIEW`: 자동 승인 불가, 리뷰 필요
- `ERROR`: 인프라/실행 오류
- `SKIPPED`: 해당 경로 실행 안 함

주의: 데모 코드의 `REVIEW_REQUIRED`는 파일 상태로 쓰지 않는다. 실제 파일 상태는 `PENDING_REVIEW`로 기록하고, job 단위 `overall_decision`에서만 `REVIEW_REQUIRED`를 사용할 수 있다.

### 5.3 CodeGrade

- `A`: 설정성 코드, AST 재생성 가능
- `B-1`: 1차 구현에서는 정형 모델 코드, 허용 API만 사용하고 제한 런타임 gate를 통과한 경우
- `B-2`: 정형 구조지만 미등록 API 또는 문맥상 리뷰 필요 요소 포함
- `C`: 동적/난독화/비정형
- `N/A`: 코드 파일 아님

### 5.4 ReviewAction

- `AUTO_APPROVE_REGENERATED`: A 등급 재생성 결과 자동 승인
- `AUTO_APPROVE`: B-1 자동 승인
- `SECURITY_OWNER_GATE`: B-2 보안 담당자 게이트
- `MANUAL_REVIEW_REQUIRED`: C 수동 리뷰
- `BLOCK_IMMEDIATELY`: 위험 요소 즉시 차단

## 6. 코드 파일 역할 분류

검증 시작 전에 `.py` 파일을 먼저 역할 기반으로 분류한다. 이 단계는 과차단을 줄이고, 같은 API도 파일 성격에 따라 다르게 해석하기 위해 필요하다.

### 6.1 설정형

대표 파일:

- `configuration_*.py`
- `generation_config.py`

구조 신호:

- `PretrainedConfig` 상속
- `model_type` 존재
- `__init__()` 중심
- `forward`, `generate`, `__call__` 같은 실행 메서드 없음

정상 역할:

- hidden size, layer 수, attention head 수, vocab size, dropout, rope 설정, token id, text/vision 하위 config 같은 값 저장

기본 처리:

- A 후보
- 단순 속성 저장이면 원본 실행 없이 AST에서 구조 추출 후 깨끗한 config 코드 재생성
- 단순 상수 계산과 `self.xxx` 속성 기반 계산만 제한적으로 허용
- 외부 파일/환경/네트워크 의존, helper method 호출, 외부 모듈 함수 호출이 의미를 바꾸면 A 제외
- 외부 호출이 있어도 숫자/문자열 상수 조합처럼 AST에서 완전히 해석 가능한 경우만 허용 후보이며, 해석 불가하면 B-2/PENDING_REVIEW

### 6.2 모델 실행형

대표 파일:

- `modeling_*.py`
- 일부 `generation_*.py`

구조 신호:

- `nn.Module` 또는 `PreTrainedModel` 상속
- `forward()` 존재
- embedding, attention, MLP, normalization, residual, task head 등 모델 계산 구조

기본 처리:

- B-1/B-2/C 중심
- 가장 엄격하게 검증
- 파일/네트워크/프로세스/동적 실행 primitive는 자동 승인 불가
- 즉시 위험 API는 whitelist 여부와 무관하게 `BLOCK`
- `open`, `os.path`, `Path` 같은 문맥 의존 API는 whitelist에 단순 등록하지 않고 context analyzer에서 호출 방식, 인자, 대상 경로, 데이터 흐름을 검증

### 6.3 입력 전처리/변환형

대표 파일:

- `tokenization_*.py`
- `processing_*.py`
- `feature_extraction_*.py`
- `image_processing_*.py`
- `video_processing_*.py`

정상 역할:

- 문자열, 이미지, 오디오, 비디오를 모델 입력 형식으로 변환
- tokenizer, image processor, video processor, feature extractor를 묶어 최종 입력 dict 구성
- chat template, special token, offset mapping, placeholder token, media grid 계산 처리 가능

기본 처리:

- 1차 구현 범위 제외
- 역할과 subtype만 분류하고 자동 승인하지 않는다.
- 공통 AST/API 분석에서 즉시 위험 API가 나오면 `BLOCK` 가능
- 위험이 확정되지 않아도 tokenizer/processor 전용 의미 검증 정책이 확정되기 전까지는 `PENDING_REVIEW` 또는 `SKIPPED`

세부 subtype:

- `TOKENIZER`: `tokenization_*.py`, tokenizer base class, tokenizer bundle 참조
- `PROCESSOR`: `processing_*.py`, `ProcessorMixin`, `apply_chat_template`
- `IMAGE_PROCESSOR`: `image_processing_*.py`
- `VIDEO_PROCESSOR`: `video_processing_*.py`
- `FEATURE_EXTRACTOR`: `feature_extraction_*.py`
- `PREPROCESS_HELPER`: 전처리 보조 함수/파일

역할 값은 크게 `PREPROCESSING`으로 유지하되, 반드시 `preprocess_kind`를 함께 기록한다. `PREPROCESSING`만으로는 tokenizer semantic check와 processor invariant check를 안정적으로 분기할 수 없다.

### 6.4 보조/변환/패키징형

대표 파일:

- `convert_*.py`
- `helper`, `utils`, packaging 관련 파일
- `__init__.py` 중 top-level 실행 코드가 있거나 동적 import/export를 수행하는 파일

정상 역할:

- 체크포인트 변환
- 패키징/공개 심볼 export
- 런타임 추론 본체가 아닌 보조 코드

기본 처리:

- 1차 구현 범위 제외
- 일반 승인 경로에서 제외하는 것이 기본 원칙
- `convert_*`는 내부 승인된 변환 환경에서만 별도 실행하는 것이 원칙
- `__init__.py`는 무조건 차단하지 않는다. 단순 상대 import, `__all__`, version constant, 클래스 export만 있으면 `INIT_EXPORT_ONLY` subtype으로 분류할 수 있지만, 1차 구현에서는 자동 승인하지 않는다.
- `__init__.py`에 top-level call, 동적 import, 파일/네트워크/환경 접근이 있으면 B-2/C/BLOCK으로 올린다.
- helper/utils는 이름만으로 승인하지 않고 실제 AST/API/context 결과로 등급을 정한다.

## 7. 검증 0: config와 tokenizer_config 트리거 라우팅

`config.json`과 `tokenizer_config.json`은 코드 실행을 유도할 수 있는 필드를 포함할 수 있다. config validator는 이 필드를 탐지하고 참조된 `.py` 파일을 코드 검증 경로로 강제 연결한다.

### 7.1 trigger fields

- `auto_map`
- `custom_pipelines`
- `trust_remote_code`
- tokenizer custom class 참조
- processor custom class 참조
- 허용 필드 whitelist 밖의 code reference 후보

### 7.2 라우팅 규칙

- trigger field가 없고 schema가 유효하면 config 결과는 `PASS`
- trigger field가 있으면 참조 `.py`를 `PYTHON` artifact로 연결
- 참조 `.py` 중 하나라도 `BLOCK`이면 config 결과도 `BLOCK`
- 참조 `.py` 중 하나라도 `PENDING_REVIEW`이면 config 결과도 `PENDING_REVIEW`
- 참조 파일이 없으면 `CONFIG_REFERENCED_CODE_ROUTED`와 누락 details를 남기고 `PENDING_REVIEW` 또는 정책상 `BLOCK`

## 8. 검증 1: CODE_AST_SCAN

AST 검증은 코드 실행 없이 문법 트리만 분석한다.

### 8.1 공통 추출 항목

- import 목록
- class 목록과 base class
- function/method 목록
- `forward`, `generate`, `__call__`, `__init__` 존재 여부
- 호출 API 목록
- 위험 import
- 위험 call
- 동적 패턴
- 난독화 패턴
- 문맥 의존 API 후보
- 파일 역할 분류 결과

이 단계에서 문맥 의존 API는 safe/review/block으로 판정하지 않는다. AST 단계는 `open`, `os.path`, `Path.read_text` 같은 호출을 후보로 추출해 다음 API 정책 단계에 넘기는 역할만 한다.

### 8.2 즉시 차단 후보

다음은 자동 승인 경로에서 즉시 차단한다.

- `eval`
- `exec`
- `compile`
- `__import__`
- `importlib` 기반 동적 import
- `os.system`
- `os.popen`
- `os.exec*`
- `os.spawn*`
- `subprocess.*`
- `socket.*`
- 명시적 외부 네트워크 호출
- `torch.load`
- `pickle.load`
- `numpy.load`

### 8.3 동적/난독화 패턴

다음은 기본적으로 C 등급 또는 차단 후보이다.

- `getattr`, `setattr`, `delattr`
- `type(name, bases, dict)` 형태의 3인자 동적 클래스 생성
- 조건부 import
- `chr`, `ord`, `bytes.decode` 기반 문자열 복원
- `globals()[name]`, `locals()[name]`, `obj.__dict__[name]`
- 런타임 문자열 조합으로 호출 대상 결정

단, 전처리/processor 계열에서 정상 dispatcher 패턴일 가능성이 있는 경우에도 자동 승인하지 않고 `PENDING_REVIEW` 이상으로 올린다.

## 9. 문맥 의존 API 분석

`open`, `os`, `Path`는 이름만으로 위험 여부를 확정하지 않는다. 호출 방식, 인자, 파일 역할, 경로 출처, 데이터 흐름을 함께 본다.

문맥 의존 API 검사는 별도의 독립 검증 단계가 아니라 검증 2인 API 정책 검사 내부의 하위 단계다.

실행 흐름:

```text
검증 1 CODE_AST_SCAN
  -> 문맥 의존 API 후보만 추출

검증 2 API_POLICY_SCAN
  -> contextual_exact/contextual_prefix 매칭
  -> code_context.py 디스패처 호출
  -> safe/review/block 판정

검증 3 grade decision
  -> context 결과를 A/B-1/B-2/C/BLOCK에 반영
```

문맥 의존 API는 일반 whitelist에 넣지 않는다. whitelist는 이름만으로 허용 가능한 exact API를 다루고, `CONTEXTUAL` API는 `code_context.py`에서 별도 판정한다. 따라서 모델 실행형에서 `open`, `os.path`, `Path`가 필요하더라도 단순 whitelist 등록이 아니라 context analyzer의 safe/review/block 결과를 등급 판정에 반영한다.

### 9.0 구현 원칙: API 유형별 함수 분리

`code_context.py`는 문맥 의존 API 판정을 하나의 거대한 함수로 구현하지 않는다. API 유형별 분석 함수를 분리하고, 최상위 디스패처가 호출을 라우팅하는 구조를 사용한다.

권장 함수 구조:

- `analyze_open_call(...)`
- `analyze_os_call(...)`
- `analyze_path_call(...)`
- `analyze_env_access(...)`
- `analyze_network_call(...)`
- `analyze_file_mutation_call(...)`
- `analyze_contextual_api_calls(...)`  # 디스패처

각 함수는 최소한 다음 필드를 포함한 공통 결과 구조를 반환한다.

- `api`
- `category`
- `decision` (`safe`, `review`, `block`)
- `reason_code`
- `evidence` (인자, 경로 출처, 데이터 흐름 요약)

최상위 디스패처는 AST/API 스캔에서 전달된 contextual call 목록을 순회하면서 API 유형에 맞는 분석 함수를 호출하고, 결과를 `context_api_scan`에 누적한다.

### 9.1 open 분석

확인 항목:

- 읽기 모드인지 쓰기/append 모드인지
- 경로가 상수인지 동적 값인지
- 패키지 내부 상대 경로인지 외부 절대 경로인지
- 파일명이 vocab, merges, tokenizer, config, json, txt 등 일반 리소스인지
- 대상이 pickle, bin, 임의 binary인지
- 경로가 환경 변수, 사용자 입력, 네트워크 입력에서 왔는지
- 경로 값이 함수 인자, config field, 외부 입력 dict, 환경 변수에서 흘러왔는지

판정:

- 패키지 내부 상수 리소스 read-only -> 제한 허용 후보
- 경로가 동적이나 쓰기 없음 -> B-2 후보
- 쓰기/삭제/외부 경로/민감 경로 -> C 또는 BLOCK

### 9.2 os 분석

분류:

- path helper: `os.path.join`, `dirname`, `basename`, `exists`
- env access: `os.getenv`, `os.environ`
- file mutation: `remove`, `rename`, `replace`, `chmod`, `chdir`
- command exec: `system`, `popen`, `exec*`, `spawn*`

판정:

- path helper -> 파일 역할에 따라 허용 후보 또는 B-2
- env access -> B-2 이상
- file mutation -> C 또는 BLOCK
- command exec -> BLOCK

### 9.3 requests/network 분석

기본 정책:

- 모델 검증/추론 코드 내부에서 외부 네트워크는 금지
- metadata 조회 등 정상 가능성이 있더라도 검증 엔진 내부에서 대신 수행해야 한다
- 코드 파일 내부 네트워크 호출은 기본 `BLOCK`
- 예외를 두려면 스캔 대상 코드가 아니라 검증 엔진의 통제된 downloader/metadata fetcher에서 처리한다.

## 10. 검증 2: API 화이트리스트

API 화이트리스트는 코드 검증의 핵심 정책이다. 허용된 API만 자동 승인 후보가 될 수 있다. 검증 2는 단순 whitelist 조회만 하지 않고, AST에서 추출한 호출을 API 정책 순서에 따라 분류한 뒤 문맥 의존 API는 context analyzer로 넘긴다.

### 10.1 API 분류

- `ALLOWED`: 현재 whitelist에 등록된 안전 API
- `BLOCKED`: 명시적으로 금지된 API
- `UNREGISTERED`: whitelist에 없는 API
- `CONTEXTUAL`: 이름만으로 판단할 수 없어 문맥 분석이 필요한 API

### 10.2 API 정책 판정 순서

검증 2의 판정 순서는 반드시 아래와 같이 고정한다.

1. 호출 대상 해석 실패 + 동적/난독화 패턴 존재 -> `C/PENDING_REVIEW`, 위험 패턴이면 `BLOCK`
2. `blocked_exact` 또는 `blocked_prefix` 매칭 -> `BLOCK`
3. 네트워크/프로세스/역직렬화/native loading 계열 -> 기본 `BLOCK`
4. `contextual_exact` 또는 `contextual_prefix` 매칭 -> context analyzer로 `safe/review/block` 판정
5. `allowed_exact` 매칭 -> `ALLOWED`
6. 그 외 -> `UNREGISTERED`, `B-2/PENDING_REVIEW`

주의:

- `BLOCKED`와 위험 범주가 `ALLOWED`보다 항상 우선한다.
- 문맥 의존 API가 `safe`이면 B-1 후보를 유지할 수 있다.
- 문맥 의존 API가 `review`이면 B-2/PENDING_REVIEW로 올린다.
- 문맥 의존 API가 `block`이면 즉시 `BLOCK`으로 올린다.
- 목록에 없는 API는 안전한 API가 아니라 `UNREGISTERED`다.

### 10.3 허용 API 예시

- `torch.nn.Linear`
- `torch.nn.Conv2d`
- `torch.nn.LayerNorm`
- `torch.nn.Embedding`
- `torch.nn.Dropout`
- `torch.nn.functional.relu`
- `torch.nn.functional.gelu`
- `torch.nn.functional.softmax`
- `torch.tensor`
- `torch.zeros`
- `torch.ones`
- `torch.arange`
- `torch.cat`
- `torch.stack`
- `torch.reshape`
- `transformers.PreTrainedModel`
- `transformers.PretrainedConfig`

초기 구현에서는 broad prefix allowlist를 피한다. 예를 들어 `torch.nn.*`, `torch.Tensor.*` 전체를 한 번에 허용하면 API 단위 whitelist 원칙이 약해진다. 첫 구현은 exact allowlist 중심으로 시작하고, prefix rule이 필요하면 아래 조건을 함께 둔다.

- blocked exact API가 항상 prefix allow보다 우선한다.
- `load`, `save`, `open`, `download`, `exec`, `compile`, `jit`, `distributed`, `rpc`, `hub` 같은 위험 키워드를 포함하면 자동 허용하지 않는다.
- prefix rule은 테스트로 확인된 좁은 namespace에만 둔다.
- prefix rule로 허용된 API도 `details.api_scan.allowed_by_prefix`에 별도 기록한다.

### 10.4 차단 API 예시

- `torch.load`
- `pickle.load`
- `numpy.load`
- `subprocess.run`
- `subprocess.Popen`
- `os.system`
- `requests.post` 등 외부 전송 API

### 10.5 미등록 API 처리

미등록 API는 자동 승인하지 않는다.

처리:

- `PendingApiRecord` 후보 생성
- namespace, 위험 키워드, 공식 문서 여부, 사용 위치를 기록
- 파일 등급은 기본 B-2
- 보안 담당자 승인 전 whitelist 반영 금지

LLM은 승인 판단자가 아니라 리뷰 설명 보조기로만 사용할 수 있다. 최종 승인 여부는 결정론적 규칙과 사람의 리뷰에 따라야 한다.

## 11. 검증 2.5: tokenizer 의미 검증

`tokenization_*.py`는 단순 코드 실행 위험보다 입력 의미 변조 위험이 크다. 따라서 일반 AST/API 검증과 별도로 tokenizer bundle 단위 의미 검증이 필요하다.

단, tokenizer 의미 검증은 1차 구현 범위가 아니다. 현재 단계에서는 역할을 `PREPROCESSING` + `TOKENIZER`로 분류하고, 즉시 위험 API가 있으면 `BLOCK`, 그 외에는 `PENDING_REVIEW` 또는 `SKIPPED`로 남긴다. 아래 내용은 후속 설계 기준이다.

### 11.1 검증 단위

단일 `.py`가 아니라 다음 파일 묶음을 tokenizer bundle로 본다.

- `tokenization_*.py`
- `tokenizer.json`
- `tokenizer_config.json`
- `special_tokens_map.json`
- `vocab.json`
- `merges.txt`
- `chat_template`

### 11.2 고유 위험

- 정규화/분해/치환 악용
- zero-width 문자, 전각/반각, homoglyph, 조합 문자 처리 왜곡
- special token / role token 경계 조작
- `AddedToken`의 `lstrip`, `rstrip` 동작 조작
- `split_special_tokens=True`
- offset mapping 교란
- token 수 팽창
- truncation 유도
- decode/log 착시
- user/system/assistant role 경계 혼동

### 11.3 검증 항목

- tokenizer semantic fuzz corpus 실행
- `encode -> ids -> decode` 변화 기록
- `special_tokens_mask` 기록
- `offset_mapping` 일관성 검사
- tokens-per-char 비율 검사
- `num_special_tokens_to_add` 검사
- truncation/overflow 임계치 검사
- chat template에서 system/assistant/user token 삽입 여부 검사
- 감사 로그 decode 시 `skip_special_tokens=True`만 사용하지 않도록 원본 control token 가시화

### 11.4 판정

- 후속 구현에서 의미 변경 신호가 정책 범위 내이고 API도 안전하면 B-1 가능
- control token, chat template, offset, 길이 관련 이상은 B-2 이상
- role 경계 조작, 숨은 system prompt 삽입, 과도한 token 팽창은 C 또는 BLOCK
- 선행 구현 단계에서 semantic check skeleton이 아직 없거나 실행되지 않은 경우, `TOKENIZER` subtype은 B-1 자동 승인으로 보내지 않는다. 이 경우 `semantic_check.status = "SKIPPED"`와 함께 B-2/PENDING_REVIEW 후보로 둔다.

## 12. 검증 2.6: processor 의미 검증

`processing_*.py`는 tokenizer, image processor, video processor, feature extractor를 묶는 glue layer다. 멀티모달 입력이 실제 모델 입력 dict로 조립되는 지점이므로 고유 검증이 필요하다.

단, processor 의미 검증은 1차 구현 범위가 아니다. 현재 단계에서는 역할을 `PREPROCESSING` + processor 계열 subtype으로 분류하고, 즉시 위험 API가 있으면 `BLOCK`, 그 외에는 `PENDING_REVIEW` 또는 `SKIPPED`로 남긴다. 아래 내용은 후속 설계 기준이다.

### 12.1 고유 위험

- placeholder token과 이미지/비디오 개수 불일치
- `pixel_values`, `image_grid_thw`, `video_grid_thw` 불일치
- 외부 URL/Path 접근
- 로컬 파일 접근
- chat template 조작
- 초고해상도 이미지, 긴 비디오, 과도한 프레임으로 인한 DoS
- 하위 tokenizer/image processor/video processor 바꿔치기
- 하위 구성요소 재귀 검증 누락

### 12.2 검증 항목

- placeholder token 수와 media item 수 일치
- grid shape와 media tensor shape 일치
- 최대 이미지 수, 최대 프레임 수, 최대 해상도, 최대 오디오 길이 제한
- URL fetch 금지 또는 allowlist 제한
- 임시 검증 디렉터리 밖 local path 접근 금지
- `apply_chat_template`와 Jinja template 변경 감지
- 하위 processor/tokenizer 참조 추적

### 12.3 판정

- 후속 구현에서 정합성 통과 + 안전 API만 사용 -> B-1 후보
- 하위 구성요소 추적 필요, URL/Path 후보, 복잡한 라우팅 -> B-2
- 외부 fetch, 로컬 민감 경로 접근, placeholder 조작, 숨은 prompt 조작 -> C 또는 BLOCK
- 선행 구현 단계에서 processor invariant skeleton이 아직 없거나 실행되지 않은 경우, `PROCESSOR`, `IMAGE_PROCESSOR`, `VIDEO_PROCESSOR`, `FEATURE_EXTRACTOR` subtype은 B-1 자동 승인으로 보내지 않는다. 이 경우 B-2/PENDING_REVIEW 후보로 둔다.

## 13. 검증 3: 등급 분류

### 13.1 A

대상:

조건:

- `self.xxx = ...` 단순 할당 목록
- `attribute_map`

## 15. 추가 권장 reason code

아래 reason code는 실제 구현 전에 `HuggingMask_인터페이스정의서_v1_0_Notion.md`의 공통 reason code에 반영하는 것이 좋다. 반영 전에는 `details`에만 기록하고, 공통 `reason_entries.code`에는 기존 reason code를 사용한다.

선행 구현 단계에서는 `reason_entries.code`를 기존 공통 reason code로 제한한다. 새 코드가 필요하면 `details.findings[].code`나 `details.semantic_findings[].code`에 기록하고, 공통 인터페이스 문서가 갱신된 뒤 `reason_entries.code`로 승격한다.

| 코드 | 의미 |
|---|---|
| `FILE_ROLE_CLASSIFIED` | Python 파일 역할 분류 완료 |
| `CONTEXT_API_REVIEW` | 문맥 의존 API가 리뷰 필요 상태 |
| `CONTEXT_API_BLOCKED` | 문맥상 위험 API로 판정 |
| `TOKENIZER_SEMANTIC_DRIFT` | tokenizer 의미 변경/왜곡 가능성 |
| `CONTROL_TOKEN_POLICY_VIOLATION` | control token 또는 role token 정책 위반 |
| `OFFSET_MAPPING_ANOMALY` | 원문-토큰 offset 정렬 이상 |
| `TOKEN_LENGTH_EXPANSION` | token 수 팽창 또는 truncation 위험 |
| `PROCESSOR_INVARIANT_MISMATCH` | media placeholder/grid/tensor 정합성 위반 |
| `EXTERNAL_RESOURCE_ACCESS` | URL 또는 외부 path 접근 |
| `CHAT_TEMPLATE_CHANGED` | chat template 변경 또는 조작 후보 |
| `SUBCOMPONENT_RECURSIVE_REVIEW` | 하위 tokenizer/processor 재귀 검증 필요 |
| `AUXILIARY_CODE_REVIEW` | 보조/변환/패키징형 코드 리뷰 필요 |

## 17. 완료 기준

코드 검증 구현의 최소 완료 기준은 다음과 같다.

- `PYTHON` artifact를 `ArtifactValidationResult`로 반환한다.
- 파일 역할 분류가 설정형, 모델 실행형, 입력 전처리/변환형, 보조/변환/패키징형을 구분한다.
- 1차 코드검증 판정은 설정형과 모델 실행형에만 적용한다.
- 입력 전처리/변환형과 보조/변환/패키징형은 역할만 분류하고 자동 승인하지 않는다.
- 원본 Python 파일을 import하지 않고 AST 분석한다.
- 위험 import/call/API를 차단한다.
- 검증 1에서는 문맥 의존 API 후보를 추출하고, 검증 2에서 context analyzer로 safe/review/block을 판정한다.
- whitelist 미등록 API를 B-2와 pending 대상으로 분류한다.
- A/B-1/B-2/C 등급 판정이 인터페이스 문서와 일치한다.
- config trigger field가 참조한 `.py` 파일이 코드 검증으로 라우팅된다.
- `python -m pytest -q`가 통과한다.
