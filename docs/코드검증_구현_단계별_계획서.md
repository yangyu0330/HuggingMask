# HuggingMask 코드검증 구현 단계별 계획서

작성일: 2026-04-19
목적: Codex를 이용해 `HuggingMask`의 실제 코드 검증 기능을 작은 단위로 구현하기 위한 작업 계획

## 1. 진행 원칙

이 계획서는 한 번에 전체 검증 엔진을 만들지 않고, 테스트 가능한 작은 PR 단위로 쪼개기 위한 문서다.

원칙:

- 실제 구현은 `C:/Users/andyw/Desktop/HuggingMask`에서 진행한다.
- `C:/Users/andyw/Desktop/test_HuggingMask`는 참고용 데모와 테스트 아이디어로만 사용한다.
- 먼저 공통 schema와 `ArtifactValidationResult` 계약을 고정한다.
- 각 단계는 `python -m pytest -q`로 검증 가능해야 한다.
- proxy는 후순위이며, 초기에는 analyzer 단위 함수와 테스트로 검증한다.
- `.md` placeholder를 수정하는 것보다 실제 `.py` 구현과 pytest를 우선한다.
- 팀원이 아직 개발에 돌입하지 않은 상태이므로, 양유상 구현 범위는 코드검증 내부 계약을 먼저 고정하는 데 둔다.
- whitelist DB, 리뷰 큐 저장소, proxy endpoint는 선행 구현에서 직접 소유하지 않고 protocol, in-memory adapter, mock fixture로만 연결한다.
- 1차 코드검증 구현은 설정형(`CONFIGURATION`)과 모델 실행형(`MODELING`) 파일만 대상으로 한다.
- 입력 전처리/변환형(`PREPROCESSING`)과 보조/변환/패키징형(`AUXILIARY`)은 역할만 분류하고 자동 승인하지 않는다.

### 1.1 선행 구현 범위

양유상이 먼저 진행할 범위:

- `analyzer/schemas.py`, `analyzer/classifier.py`
- 설정형/모델 실행형 Python code role/AST/API/context validator
- config trigger field 탐지와 code routing
- analyzer orchestrator 단위 통합 테스트
- B-2/PENDING_REVIEW가 필요한 API와 out-of-scope 역할을 결과 details에 남기는 구조

선행 구현에서 제외할 범위:

- tokenizer/processor/feature extractor semantic 검증
- helper/utils/convert/packaging 코드 자동 승인 정책
- 운영용 whitelist DB와 승인 workflow
- persistent pending API store
- proxy 인증, 외부 다운로드, 실제 Hub fetch
- 원본 모델 Python 파일 import 또는 임의 실행

외부 모듈이 아직 없을 때는 `WhitelistLookup` 같은 작은 protocol을 코드검증 내부에 두고, 테스트에서는 in-memory adapter를 사용한다. 이후 팀원이 whitelist/리뷰 큐를 구현하면 adapter만 교체한다.

### 1.2 검증 실행 흐름 고정

구현 단계가 PR 단위로 나뉘어도 실제 실행 흐름은 아래 순서를 유지한다.

```text
0. config 라우팅
   - auto_map / trust_remote_code / custom_pipelines 확인
   - 참조 .py를 코드검증으로 연결

1. AST 분석
   - 원본 import 금지
   - ast.parse만 수행
   - 파일 역할 분류
   - 위험 call/import 후보 탐지
   - 동적/난독화 패턴 탐지
   - 호출 API 목록 추출
   - 문맥 의존 API 후보 추출

2. API 검사 + 문맥 의존 API 분석
   - blocked_exact / blocked_prefix 검사
   - 네트워크/프로세스/역직렬화/native loading 검사
   - contextual API면 context analyzer 실행
   - allowed_exact 검사
   - 나머지는 UNREGISTERED

3. 정적 판정
   - A 후보
   - B-1 후보
   - B-2 후보
   - C 후보
   - BLOCK

4. route별 후속 처리
   - A 후보: 원본 실행 없이 코드 재생성
   - B-1 후보: 제한 런타임 실행
   - B-2/C 후보: gVisor/Docker 샌드박스 또는 리뷰 큐
   - BLOCK: 실행하지 않음
```

문맥 의존 API 분석은 B-2로 간 뒤 하는 검사가 아니다. 검증 2에서 먼저 수행하고, 그 결과로 B-1 후보 유지, B-2/PENDING_REVIEW, BLOCK이 결정된다.

제한 런타임은 정적으로 안전해 보이는 B-1 후보를 최종 PASS시키기 위한 gate다. gVisor/Docker 샌드박스는 자동 승인 불가한 B-2/C 후보를 격리해 증거를 수집하거나 리뷰를 보조하는 환경이다. 명확한 위험 API가 발견된 파일은 실행하지 않고 즉시 BLOCK한다.

### 1.3 코드검증과 whitelist/review 담당 경계

| 영역 | 담당 | 설명 |
|---|---|---|
| API 호출 추출 | 코드검증 | AST에서 `torch.nn.Linear`, `F.relu`, `torch.load` 같은 호출 경로 추출 |
| alias resolution | 코드검증 | `import torch.nn.functional as F` -> `torch.nn.functional`로 해석 |
| 위험 API 선차단 | 코드검증 | `eval`, `subprocess`, `requests`, `torch.load` 등 명확한 위험은 whitelist 질의 전에 `BLOCK` 가능 |
| 문맥 의존 API 분석 | 코드검증 | `open`, `os.path`, `Path` 등을 context analyzer로 `safe/review/block` 판정 |
| whitelist 질의 인터페이스 | 코드검증 | `WhitelistLookup` protocol, mock/in-memory adapter 제공 |
| 실제 whitelist DB | whitelist 담당 모듈 | 허용 API 저장소, 정책 버전, 승인 상태 관리 |
| Pending API 저장 | whitelist/review 담당 모듈 | 미등록 API 등록/갱신, seen count, first_seen/last_seen 관리 |
| 보안 담당자 승인 workflow | review 담당 모듈 | 리뷰 결정, whitelist 반영, 감사 로그 연결 |
| 공식 문서/Verified Org 판단 | whitelist/review 담당 모듈 | API가 공식 문서에 있는지, 검증된 조직 사용 여부 판단 |

- `test_HuggingMask/analyzer/stage1_ast_policy.py`의 `classify_file_role()`을 참고하되 실제 enum 이름은 새 설계에 맞춘다.

- `convert_demo.py` -> `AUXILIARY`
- export-only `__init__.py` -> `AUXILIARY` + `INIT_EXPORT_ONLY`
- 애매한 파일 -> `UNKNOWN`

- dangerous calls 추출
- dynamic patterns 추출
- obfuscation patterns 추출
- class inheritance 신호 추출
- `forward`, `generate`, `__call__`, `__init__` 존재 여부 추출
- API call raw name 추출
- 문맥 의존 API 후보 추출

위험 신호:

- `eval`, `exec`, `compile`, `__import__`

- `chr`, `ord`, `bytes.decode`

테스트:

- 위험 call 차단 신호
- 조건부 import 신호

## 8. 단계 5 - API 화이트리스트 스캔 구현

목표:

- AST에서 추출한 호출을 API 단위로 `allowed`, `blocked`, `unregistered`, `contextual`로 나누고, `contextual`은 검증 2 내부에서 context analyzer로 safe/review/block 판정한다.

생성/수정 파일:

- `analyzer/validators/code_api.py`
- `analyzer/validators/code_api_policy.py`
- `tests/test_code_api.py`

구현 대상:

- API alias resolution:
  - `import torch.nn.functional as F` -> `torch.nn.functional`
  - `import numpy as np` -> `numpy`
  - `from torch import nn` -> `torch.nn`
- `WhitelistLookup` protocol
- 선행 구현용 in-memory policy adapter
- allowed exact list
- blocked exact list
- contextual API 후보
- contextual API 판정 디스패처 연결
- unregistered API 수집
- policy version 반환

초기 policy seed:

- `torch.nn.Linear`, `torch.nn.Embedding`, `torch.nn.LayerNorm`, `torch.nn.ModuleList`
- `torch.nn.functional.relu`, `torch.nn.functional.softmax`, `torch.nn.functional.gelu`
- 검토된 `torch.Tensor` 메서드 일부
- `transformers.PreTrainedModel`
- `transformers.PretrainedConfig`
- `numpy.array`, `numpy.asarray`, `numpy.zeros`, `numpy.ones`

주의:

- `torch.nn.*`, `torch.nn.functional.*`, `torch.Tensor.*` 같은 넓은 prefix allowlist를 초기 구현에 넣지 않는다.
- prefix 허용이 필요하면 별도 승인된 좁은 namespace만 사용하고, blocked exact API가 항상 우선한다.
- danger keyword가 들어간 API는 prefix에 걸려도 자동 허용하지 않는다.
- 검증 2 판정 순서는 `호출 대상 해석 실패+동적/난독화`, `blocked_exact/prefix`, `위험 범주`, `contextual`, `allowed_exact`, `unregistered` 순서로 고정한다.
- 문맥 의존 API가 `safe`이면 B-1 후보를 유지할 수 있고, `review`이면 B-2/PENDING_REVIEW, `block`이면 BLOCK으로 올린다.

차단:

- `torch.load`
- `pickle.load`
- `numpy.load`
- command/network API

테스트:

- `F.relu`가 허용 API로 해석되는지
- `torch.load`가 blocked로 잡히는지
- `torch.special.expit` 같은 신규 API가 unregistered로 잡히는지
- `open("vocab.json", "r")` 같은 contextual API가 API 단계에서 context analyzer로 라우팅되는지

완료 기준:

- API 스캔 결과가 `api_scan` dict로 serialize 가능
- 선행 구현의 in-memory policy adapter와 추후 whitelist engine 교체 지점이 분리
- `context_api_scan` 결과를 code validator details에 전달할 수 있음

Codex 요청 예시:

```text
analyzer/validators/code_api.py와 analyzer/validators/code_api_policy.py를 구현해줘. 정식 whitelist DB는 만들지 말고 WhitelistLookup protocol과 in-memory policy로 alias resolution, allowed/blocked/contextual/unregistered API 분류를 구현해줘. contextual API는 code_context 디스패처로 넘기고, 판정 순서 테스트도 추가해줘.
```

## 9. 단계 6 - 문맥 의존 API 분석 구현

목표:

- `os.path.join` -> path helper
- `os.system` -> block
- `os.environ.get` -> review

- 디스패처가 API 종류별 함수(`open/os/path/env/network/mutation`)를 정확히 호출하는지

완료 기준:

- 문맥상 block이면 grade 전에 `BLOCK` 가능

## 10. 단계 7 - 등급 판정 엔진 구현

목표:

- AST, API, context, role 결과를 합쳐 A/B-1/B-2/C를 결정한다.

주의:

- 1차 구현에서 최종 판정 대상은 설정형과 모델 실행형뿐이다.
- `PREPROCESSING`, `AUXILIARY`, `UNKNOWN`은 즉시 위험 API가 있으면 `BLOCK`, 그 외에는 자동 승인하지 않고 `PENDING_REVIEW` 또는 `SKIPPED`로 둔다.
- 모델 실행형의 최종 B-1/PASS 판정은 restricted runtime check 결과를 입력으로 받는 구조여야 한다.
- restricted runtime check가 아직 구현되지 않았으면 runtime 의존 B-1은 최종 PASS가 아니라 B-1 candidate 또는 B-2/PENDING_REVIEW로 남긴다.
- A 등급 config 검증은 원본 `configuration_*.py`를 import하거나 `to_dict()`를 호출하지 않고 AST/source metadata로만 인터페이스 보존을 확인한다.

생성/수정 파일:

- `analyzer/validators/code_validator.py`
- `tests/test_code_validator.py`

구현 대상:

- `validate_python_artifact(artifact, source, policy, whitelist_lookup, runtime_check=None)` 형태의 함수
- `CodeValidationResultDetail` 생성
- `ArtifactValidationResult` 반환
- 등급 우선순위 고정
- status/review_action/runtime_mode 매핑

판정 규칙:

- dangerous import/call/API -> `BLOCK`, `C`, `BLOCK_IMMEDIATELY`
- dynamic/obfuscation -> `PENDING_REVIEW`, `C`, `MANUAL_REVIEW_REQUIRED`
- context analyzer 결과가 `block` -> `BLOCK`, `C`, `BLOCK_IMMEDIATELY`
- context analyzer 결과가 `review` -> `PENDING_REVIEW`, `B-2`, `SECURITY_OWNER_GATE`
- unregistered API -> `PENDING_REVIEW`, `B-2`, `SECURITY_OWNER_GATE`
- 모델 실행형 B-1 조건 + context analyzer 결과가 모두 `safe` + runtime gate 통과 -> `PASS`, `B-1`, `AUTO_APPROVE`
- 모델 실행형 B-1 후보지만 runtime gate 미구현 또는 skipped -> `PENDING_REVIEW`, `B-2`, `SECURITY_OWNER_GATE`
- A 조건 + 정적 인터페이스 보존 검증 통과 -> `PASS`, `A`, `AUTO_APPROVE_REGENERATED`
- 1차 범위 밖 역할 -> 기본 `PENDING_REVIEW` 또는 `SKIPPED`

테스트:

- 단순 config -> A/PASS
- 정형 model + allowed API + runtime_check passed -> B-1/PASS
- 정형 model + allowed API + runtime_check skipped -> B-2/PENDING_REVIEW
- preprocessing role -> out-of-scope PENDING_REVIEW 또는 SKIPPED
- auxiliary role -> out-of-scope PENDING_REVIEW 또는 SKIPPED
- unregistered API -> B-2/PENDING_REVIEW
- dynamic getattr -> C/PENDING_REVIEW
- `eval` -> C/BLOCK
- `torch.load` -> C/BLOCK
- export-only `__init__.py` -> out-of-scope PENDING_REVIEW 또는 SKIPPED

완료 기준:

- `tests/test_code_validator.py` 통과
- `ArtifactValidationResult.details`에 `ast_scan`, `api_scan`, `grade_result`, `runtime_check` 포함

Codex 요청 예시:

```text
code_roles/code_ast/code_api/code_context 결과와 runtime gate 입력을 합쳐 analyzer/validators/code_validator.py를 구현해줘. 1차 판정 대상은 설정형과 모델 실행형만이야. 원본 configuration_*.py는 import하지 말고, A/B-1/B-2/C 판정과 ArtifactValidationResult 반환 테스트를 추가해줘.
```

## 20. 구현 시 Codex에게 계속 강조할 조건

Codex에 작업을 맡길 때 아래 조건을 반복해서 붙이는 것이 좋다.

```text
원본 Python 모델 파일을 import하지 마.
검증 1단계는 ast.parse만 사용해.
문맥 의존 API는 검증 1에서 후보만 추출하고, 검증 2 API 정책 검사 안에서 safe/review/block으로 판정해.
문맥 의존 API 분석은 B-2로 보낸 뒤 하는 검사가 아니라 B-1/B-2/BLOCK을 가르는 검증 2 하위 분석이야.

gVisor/Docker 샌드박스는 B-2/C 후보의 증거 수집과 리뷰 보조용이지 자동 승인 증명이 아니야.
명확한 위험 API가 있으면 샌드박스도 실행하지 말고 즉시 BLOCK해.
실제 저장소의 상태값은 PASS/BLOCK/PENDING_REVIEW/ERROR/SKIPPED로 맞춰.

proxy에는 검증 로직을 넣지 말고 analyzer에 둬.
```
